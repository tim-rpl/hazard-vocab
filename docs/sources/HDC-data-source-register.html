Derived, not sourced

Estimated fire footprints and projected smoke plumes are computed in the browser, not fetched. Both are always labelled as estimates in the interface. An estimated footprint is suppressed geometrically the moment a real perimeter covers the same ground, and acreages of neighbouring fires are never summed, because that is an agency determination rather than an arithmetic one.

The honest residual — stated in the product, not just here

Oregon's statewide layer is populated by local input. A county that publishes only to its own on-premises server, or only through a proprietary vendor app, cannot appear in it and therefore cannot appear here either. The app never fabricates a boundary to fill that gap.

Two rules follow from that. A zone whose level cannot be parsed is drawn grey and labelled LEVEL UNREADABLE rather than dropped. And an empty result states explicitly that this does not mean no orders are in force, directing the user to their county sheriff — emptiness is never presented as safety.

This is also the single gap that a state sponsor could close outright, by opening the county feeds that are currently unreachable.

Why both triggers run on the same series — a real defect, found and fixed

Until build v84 the Oregon trigger was tested against the composite us_aqi value while Washington's ran on PM2.5. Ozone alone can push a composite index past 101 with no smoke present, which produced an impossible result: a longer Oregon exceedance window than Washington's, when Washington's lower threshold must always give the longer window.

Both rules are PM2.5-specific — Oregon's OAR 437-002-1081 sets 35.5 µg/m³, which is what AQI 101 means for PM2.5, and Washington's WAC 296-820 sets 20.5 µg/m³. Testing both on one series makes the correct ordering structural rather than coincidental. The regression test feeds 48 hours of composite AQI 160 with PM2.5 at 8 and asserts that both exceedance lists come back empty.

It is recorded here because a register that lists only what a source provides, and never how it was misused, is not much use to an engineer inheriting the system.

One further note on access: EPA's keyed AirNow API exists and is documented as the fallback, but is deliberately not used. A key would ship visible in a client-side application. The public feature services above carry the same instrument data without that exposure.

Why the geopotential heights matter

The inversion is measured, not inferred. Central Oregon sits at 850–1300 m above sea level, which means the 925 hPa pressure level — roughly 800 m — is routinely underground at Bend. Fetching the geopotential height alongside the temperature at each level lets the app discard any level below the site's own elevation before comparing temperatures. Without that, the app would confidently report an inversion using a reading from beneath the ground the user is standing on.

Cold-air pooling comes from the terrain model rather than any weather grid, because a 3 km forecast cell cannot distinguish a ridge top from the valley floor a mile away, and those two places behave completely differently. The app samples elevation rings at 2 / 4.5 / 8 km on 24 bearings and uses the median rise — one peak on one bearing is a mountain to look at, not a basin to sit in.

Because the road layer is raster, its labels are pixels rather than text. Every other label in the application responds to the four text sizes, the high-contrast mode and the Easy Colors palette. Two things to be explicit about

Occupancy is modelled, not surveyed, and the interface says so. It also states that an empty area does not mean a safe area — the dataset's coverage is not a census.

Aircraft

Three independent ADS-B networks in a fallback chain. If the first is down, the next is tried without any user action — the only category in the app with redundancy at the provider level, because these feeds are the least reliable of any used.

OpenSky NetworkResearch ADS-B network Third source, identical use. Final fallback KeylessFallback
A feed problem that became a correctness rule

These feeds do not guarantee an aircraft identifier. Rows arrive with the ICAO hex field blank, and until build v89 that produced a silent wrong answer: every aircraft without an identifier collapsed onto the same record, so the map could follow one plane while the panel described another.

The rule that came out of it: an identity is built from the first field that actually exists — ICAO hex, then alternative ICAO fields, then registration, then callsign, then a position-derived fallback — and if none of those yield anything, the aircraft is not rendered at all. The app will not guess an identity and will not show a card it cannot stand behind.

Category 10

Curated content — written, not fetched

One file, places.js, holds everything a machine feed cannot supply: the interpretation. It is deliberately separated from application logic so a subject-matter expert can edit it without touching a line of code.

What it contains

  • 27 burn-scar narratives — what happened on specific ground, in specific years.
  • 10 year narratives — the character of each fire season.
  • 15 great burns — the century-scale landmark fires.
  • Named landscapes, waters, viewpoints and the Field Day categories: fishing, elk, deer, snow, roads.
  • The opening map centre and default locations.

The rule that governs it

Honest data, never fabricated. Directions, access notes and place descriptions are researched and written, never invented to fill a gap. Where content does not exist for a region, the app has less to say about that region — it does not manufacture something plausible.

Current coverage is Central-Oregon-weighted. Statewide enrichment is a curation effort, not an engineering one, and is named as outstanding rather than implied to be complete.

The feeds supply what is happening. This file supplies what it means.

Summary

What this list implies

Operationally

  • No credential exists anywhere in the codebase. Nothing to rotate, leak, meter or expense, and no bill that grows when public attention spikes during an emergency.
  • Nothing is mirrored. Every reading comes from the publishing agency at the moment it is displayed. There is no intermediate copy to fall out of date.
  • Failure is loud. Feeds are expected to fail under load, so the app names the failure — "live service not answering: too many requests" — draws the last-known official outlines under a LAST KNOWN status with the save time stated, and refuses any cache older than 36 hours.

Structurally

  • Every browser talks directly to each agency. That is the design's strength and its scaling limit: ten thousand people opening the map is ten thousand queries against the same government services. The edge cache and pre-baked snapshots that fix this are designed and costed but not yet built.
  • One planned feature breaks the keyless property. Road closures, via the state transportation APIs, require a free registered key. The answer is to hold it server-side in the edge cache — which is an argument for building that layer, not against the data.
  • Three sources are not yet confirmed live. They are listed as unverified rather than quietly presented as working.
How verification status is assigned — and why some of it is honest rather than flattering

The development environment blocks outbound access to every live data host. Endpoints, item IDs and field schemas are therefore confirmed against each publisher's own documentation and tested against payload-shaped fixtures, but the first real contact with several services happens in the browser.

Confirmed live means observed returning data in the running application. Documented means the endpoint and schema were verified against the publisher's documentation and the code handles the shape correctly, but it has not yet been watched working end to end. Unverified means neither. Sources in the second and third categories carry defensive handling — field-name probing, full-field retries, and a visible failure state rather than a silent blank.

Scope. This register covers build v89 of High Desert Command, August 2026. It lists external data sources only; computed products — projected smoke plumes, estimated fire footprints, terrain viewsheds, the 5-3-1 landmark card, threshold timelines and the inversion assessment — are derived in the browser from the sources above and are labelled as models wherever they appear in the application.
